# 来源学习、三餐规划与报餐

先读取用户当前的有效营养方案、真实记录和已确认食品标签。用户未要求改方法时，换菜单不能偷偷改算法或把作者方法替换为近似的固定宏量数值。未明确选择作者方法，不默认应用任何示例作者的系数。

学习来源由 `video-learning` 负责，个人饮食由本 Skill 负责。来源说明、个人接受的目标、菜单估算和实际摄入分别保存；结果由 Agent 在对话中呈现。学习示例不激活目标。

## 三餐规划数据

营养方案以独立 JSON 保存，结构为 `schema:1`、`food_library:[]`、`current_plan`。current_plan 使用 `version/title/target_version/target/meals`；target 包含 `version/method/macros`；meals 每项为 `name/foods`，food 为 `name/portion/macros`。宏量字段为 `calories/protein_g/carbs_g/fat_g`，未知值用 null。目标版本必须匹配，否则不做达标判断。保留历史方案文件。

方案确认后由 Agent 直接写出新的版本化 JSON 到营养目录；不得覆盖历史方案，也不得把菜单记成摄入。

## 报餐规则

- 无照片也可报餐。优先用用户描述、实际品牌口味和标签；图片只是补充证据。
- 掌、拳、碗等参照保留原话，不能当成统一精确克数；不凭空添加用户明确没有的油或酱。
- 同一食品标签可复用，标签冲突保留两者来源并待校准。原图只保存用户自己的资料目录，不进入公共包。
- 餐前估算与饭后候选分开；需用户确认才入账，确认后可撤销。处理完成不等于吃过。
- 复盘只在缺少时用一句话询问体感，不重复收集已知反馈，不额外强制填写体感表单。

照片与其他材料由当前 Agent 在对话中分析；候选值必须经用户确认才入账，不能把人工候选冒充 AI 识别。不启用常驻轮询，不上传照片到外部服务。
